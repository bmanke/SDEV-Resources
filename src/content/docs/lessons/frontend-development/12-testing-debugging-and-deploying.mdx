Writing code is only part of the job. You also need to **prove it works** (tests), **find out why it doesn't** (debugging),
and **put it in front of users** (deployment). This final lesson covers all three.

## Part 1: Automated testing with Vitest

A test is code that runs your code and checks the result. Once written, tests run in seconds and tell you immediately if a change broke something.

### Setup

```sh
npm install -D vitest jsdom
```

```js title="vitest.config.js"
import { defineConfig } from 'vitest/config';

export default defineConfig({
  test: {
    environment: 'jsdom',     // simulates a browser, including document and custom elements
  },
});
```

```json title="package.json (excerpt)"
{
  "scripts": {
    "test": "vitest",
    "test:run": "vitest run"
  }
}
```

`npm test` starts watch mode, which re-runs affected tests every time you save. `npm run test:run` runs once and exits (good for automation).

### Your first test

Test files end in `.test.js`. A test has a name, runs some code, and **asserts** what should be true with `expect`.

```js title="src/utils/format.js"
export function formatPrice(amount) {
  return `$${amount.toFixed(2)}`;
}

export function isValidEmail(value) {
  return /^[^\s@]+@[^\s@]+\.[^\s@]+$/.test(value);
}
```

```js title="src/utils/format.test.js"
import { describe, test, expect } from 'vitest';
import { formatPrice, isValidEmail } from './format.js';

describe('formatPrice', () => {
  test('adds a dollar sign and two decimals', () => {
    expect(formatPrice(5)).toBe('$5.00');
  });

  test('rounds to cents', () => {
    expect(formatPrice(19.999)).toBe('$20.00');
  });
});

describe('isValidEmail', () => {
  test.each(['a@b.co', 'first.last@example.com'])('accepts %s', (email) => {
    expect(isValidEmail(email)).toBe(true);
  });

  test.each(['', 'plain', 'a@b', 'a b@c.com'])('rejects "%s"', (email) => {
    expect(isValidEmail(email)).toBe(false);
  });
});
```

Common assertions:

| Assertion | Checks |
| --------- | ------ |
| `expect(a).toBe(b)` | Strict equality, for numbers, strings and booleans |
| `expect(a).toEqual(b)` | Deep equality, for objects and arrays |
| `expect(list).toContain(x)` | An item is in an array or string |
| `expect(fn).toThrow()` | A function throws |
| `expect(a).toBeTruthy()` / `toBeNull()` | Truthiness, null |
| `expect(a).not.toBe(b)` | Any assertion, negated |

### The shape of a good test: arrange, act, assert

```js
test('removes a task by id', () => {
  // Arrange: set up the data
  const tasks = [{ id: 1 }, { id: 2 }];

  // Act: run the code under test
  const result = removeTask(tasks, 1);

  // Assert: check the outcome
  expect(result).toEqual([{ id: 2 }]);
});
```

Test one behaviour per test, give it a name that reads like a sentence, and test the edges: empty input, zero, very large values, and bad input.

<Aside type="tip" title="Pure functions are easy to test">
This is why lesson 3 recommended functions that take inputs and return outputs. If logic is tangled up with the DOM, pull it out into a plain function and test that.
</Aside>

### Testing the DOM

With the `jsdom` environment, `document` exists in your tests.

```js title="src/render.js"
export function renderTasks(listEl, tasks) {
  listEl.replaceChildren();
  for (const task of tasks) {
    const li = document.createElement('li');
    li.textContent = task.text;
    li.classList.toggle('done', task.done);
    listEl.append(li);
  }
}
```

```js title="src/render.test.js"
import { describe, test, expect, beforeEach } from 'vitest';
import { renderTasks } from './render.js';

describe('renderTasks', () => {
  let list;

  beforeEach(() => {
    document.body.innerHTML = '<ul id="list"></ul>';   // fresh page for every test
    list = document.querySelector('#list');
  });

  test('creates one item per task', () => {
    renderTasks(list, [
      { text: 'Buy milk', done: false },
      { text: 'Walk dog', done: true },
    ]);
    expect(list.children).toHaveLength(2);
  });

  test('marks finished tasks', () => {
    renderTasks(list, [{ text: 'Walk dog', done: true }]);
    expect(list.firstElementChild.classList.contains('done')).toBe(true);
  });

  test('replaces old content', () => {
    renderTasks(list, [{ text: 'One', done: false }]);
    renderTasks(list, [{ text: 'Two', done: false }]);
    expect(list.textContent).toBe('Two');
  });
});
```

### Testing a web component

Import the file (which registers the element), add it to the page, then inspect its shadow root and dispatch real interactions.

```js title="src/components/book-card.test.js"
import { describe, test, expect, beforeEach, afterEach, vi } from 'vitest';
import './book-card.js';

describe('<book-card>', () => {
  let card;

  beforeEach(() => {
    card = document.createElement('book-card');
    card.setAttribute('title', 'Dune');
    card.setAttribute('author', 'Frank Herbert');
    document.body.append(card);                       // triggers connectedCallback
  });

  afterEach(() => {
    card.remove();
  });

  test('renders the title and author', () => {
    expect(card.shadowRoot.querySelector('.title').textContent).toBe('Dune');
    expect(card.shadowRoot.querySelector('.meta').textContent).toBe('by Frank Herbert');
  });

  test('updates when an attribute changes', () => {
    card.setAttribute('title', 'Emma');
    expect(card.shadowRoot.querySelector('.title').textContent).toBe('Emma');
  });

  test('dispatches book-read when the button is clicked', () => {
    const handler = vi.fn();                          // a spy that records calls
    document.addEventListener('book-read', handler);

    card.shadowRoot.querySelector('button').click();

    expect(handler).toHaveBeenCalledTimes(1);
    expect(handler.mock.calls[0][0].detail).toEqual({ title: 'Dune' });
    document.removeEventListener('book-read', handler);
  });
});
```

### Testing async code and fetch

Do not call a real server in unit tests. Replace `fetch` with a controlled fake.

```js title="src/api/books.test.js"
import { test, expect, vi, afterEach } from 'vitest';
import { getBooks } from './books.js';

afterEach(() => {
  vi.unstubAllGlobals();
});

test('returns the books from the server', async () => {
  vi.stubGlobal('fetch', vi.fn().mockResolvedValue({
    ok: true,
    text: async () => JSON.stringify([{ id: '1', title: 'Dune' }]),
  }));

  await expect(getBooks()).resolves.toEqual([{ id: '1', title: 'Dune' }]);
});

test('throws when the server returns an error', async () => {
  vi.stubGlobal('fetch', vi.fn().mockResolvedValue({
    ok: false,
    status: 500,
    statusText: 'Server Error',
    text: async () => '',
  }));

  await expect(getBooks()).rejects.toThrow('500');
});
```

### When tests fail

Read the failure message: it shows the **expected** and **received** values and the line of the assertion. Common causes:

| Symptom | Likely cause |
| ------- | ------------ |
| `document is not defined` | The environment is not `jsdom`. Check `vitest.config.js`. |
| Shadow root is `undefined` | The element is not registered (missing import) or not attached to `document.body`. |
| A test passes alone but fails with others | Leftover state. Reset the DOM in `beforeEach`. |
| `Cannot find module` | Wrong relative path or missing `.js` extension. |

## Part 2: Debugging

Debugging is a method, not a talent.

<Steps>

1. **Reproduce it.** Find the exact steps that trigger the problem.
2. **Locate it.** Which function or line is involved? The console error usually tells you.
3. **Form a hypothesis.** "I think `items` is empty here."
4. **Test the hypothesis.** Log the value or pause the code and inspect it.
5. **Fix one thing**, re-run, and confirm. Then write a test so it cannot return.

</Steps>

### Reading console errors

```text
Uncaught TypeError: Cannot read properties of null (reading 'addEventListener')
    at main.js:7:8
```

This means `document.querySelector(...)` returned `null`, because of a typo in the selector, or a script that ran before the element existed. The last line says exactly where to look.

### Browser DevTools (F12)

| Panel | Use it to |
| ----- | --------- |
| **Elements** | Inspect and edit the live DOM and CSS. See which rules apply and which are overridden. Spot shadow roots. |
| **Console** | Read errors, run JavaScript against the page, view `console.log` output. |
| **Sources** | Set breakpoints, step through code, watch variables. |
| **Network** | See every request: URL, method, status, headers, payload, timing. Essential for API bugs. |
| **Application** | Inspect `localStorage`, cookies and caches. |

### Better logging

```js
console.log('value:', value);
console.table(books);                    // arrays of objects as a table
console.error('Something failed', error);
console.group('Rendering');
console.log('items:', items.length);
console.groupEnd();
console.time('render');
renderTasks(list, tasks);
console.timeEnd('render');
```

### Breakpoints

In **Sources**, click a line number to pause there. Or write `debugger;` in your code and the browser stops at that line when DevTools is open.

While paused you can:

- Hover over variables to see their values, or add them to **Watch**.
- Step over (<kbd>F10</kbd>) to run the next line, step into (<kbd>F11</kbd>) to go inside a function call, step out (<kbd>Shift</kbd> + <kbd>F11</kbd>) to leave it.
- Look at the **Call Stack** to see how you got here.
- Type expressions in the console to try fixes.

### Debugging an API problem

1. Open **Network**, reload, and click the failing request.
2. Check the **status** (404 means the URL is wrong, 500 means the server failed, "failed" means it could not connect).
3. Look at the **payload** you sent and the **response** you received.
4. Compare the URL and method with what the API expects.

### When you are stuck

1. Re-read the error message slowly, word by word.
2. Shrink the problem: delete code until the bug disappears, then add it back.
3. Explain the problem out loud, or write it down as a question to a classmate.
4. Take a short break. A fresh look often reveals what you missed.
5. When asking for help, share the exact error, what you expected, and what you already tried.

## Part 3: Building and deploying

During development Vite serves unbundled files for speed. For visitors, you build an optimized version.

```sh
npm run build        # creates dist/ with minified, bundled files
npm run preview      # serves dist/ locally so you can check it before shipping
```

What `dist/` contains is **static files**: HTML, CSS, JavaScript, images. Any static host can serve them.

### Deployment checklist

- [ ] `npm run build` finishes without errors.
- [ ] `npm run preview` works and the console is clean.
- [ ] Tests pass (`npm run test:run`).
- [ ] No secrets (API keys, passwords) are in the code. Anything in frontend code is public.
- [ ] URLs to your API are not `localhost` in production (use an environment variable, below).
- [ ] The latest changes are committed and pushed.

### Environment variables

Vite exposes variables whose names start with `VITE_` through `import.meta.env`.

```sh title=".env.development"
VITE_API_URL=http://localhost:3000
```

```sh title=".env.production"
VITE_API_URL=https://api.example.com
```

```js
const BASE_URL = `${import.meta.env.VITE_API_URL}/books`;
```

### Hosting options

| Host | How |
| ---- | --- |
| **GitHub Pages** | A GitHub Action builds the project and publishes `dist/`. Free. |
| **Netlify / Vercel / Cloudflare Pages** | Connect your repo, set the build command to `npm run build` and the output directory to `dist`. Every push redeploys. |

### Sub-path hosting (GitHub Pages)

A GitHub Pages project site lives at `https://your-name.github.io/repo-name/`, not at the root. Tell Vite its base path, or CSS and scripts will 404:

```js title="vite.config.js"
import { defineConfig } from 'vite';

export default defineConfig({
  base: '/repo-name/',          // must match the repo name exactly, including capitals
});
```

After deploying, open the live site, check the Network panel for failed requests, and click through every page.
