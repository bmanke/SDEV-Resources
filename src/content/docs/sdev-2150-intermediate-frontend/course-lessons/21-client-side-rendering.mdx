This lesson is conceptual. You are not changing the app. You are building a mental model of what the browser does with it, because the next lesson changes it.

## Two models

A traditional multi-page application:

1. The browser requests a URL.
2. The server returns a full HTML page.
3. The browser renders that page.
4. Clicking a link requests another full HTML page.

A client-side rendered React application:

1. The browser requests a URL.
2. The server returns a small HTML shell and JavaScript assets.
3. The JavaScript loads in the browser.
4. React renders the visible UI into the page.
5. Later navigation happens without a full page reload.

The difference is who renders. In the first case the server does. In the second the browser does, after the JavaScript arrives.

## The HTML shell

Open `index.html` in the Campus Eats project.

```html
<!doctype html>
<html lang="en">
  <head>
    <meta charset="UTF-8" />
    <meta name="viewport" content="width=device-width, initial-scale=1.0" />
    <title>Campus Eats</title>
  </head>
  <body>
    <div id="root"></div>
    <script type="module" src="/src/main.jsx"></script>
  </body>
</html>
```

What is present: a root container and a script tag. What is missing: the entire visible UI. The user sees an empty page until the JavaScript runs.

This is the defining trait of CSR.

## The render chain

Open `src/main.jsx`.

```jsx
import { StrictMode } from 'react';
import { createRoot } from 'react-dom/client';
import { RouterProvider } from 'react-router';
import './index.css';
import { router } from './router';
import { ThemeProvider } from './context/ThemeProvider';

createRoot(document.getElementById('root')).render(
  <StrictMode>
    <ThemeProvider>
      <RouterProvider router={router} />
    </ThemeProvider>
  </StrictMode>
);
```

The chain:

1. The browser loads `main.jsx`.
2. React mounts into `#root`.
3. The router decides which route matches.
4. The layout and page components render.
5. The visible UI appears.

The UI is created in the browser. The server never saw a completed page.

## CSR with data mode

With the loaders from [Lesson 19](/sdev-2150-intermediate-frontend/course-lessons/19-react-router-data-mode/), the browser does more before the UI appears.

1. The browser gets the HTML shell.
2. The JavaScript loads.
3. The router matches a route.
4. The route's loader fetches data.
5. The page component renders with that data.

The loader runs before the component renders, but the whole sequence starts in the browser, after the JavaScript loads. That is still CSR.

## Observe it

Open DevTools, go to the Network tab, and reload.

Look for:

- The initial HTML document, which is small.
- The JavaScript module files.
- The CSS.
- The API request for the loader data.

The order is visible. The HTML arrives first, the JavaScript next, and the data last. The UI appears after all three.

## What CSR costs

- Delayed first content. The user sees an empty shell until the JavaScript runs.
- Heavy reliance on JavaScript. A script error is a blank page.
- Search engines and social previews see the shell, not the content, unless they execute JavaScript.

## What CSR buys

- No full page reload on navigation.
- A single JavaScript bundle, loaded once.
- Full access to the browser's APIs.

For an internal tool behind a login, CSR is often the right call. For a public page where first content matters, it is not. That is [Lesson 22](/sdev-2150-intermediate-frontend/course-lessons/22-server-side-rendering/).
